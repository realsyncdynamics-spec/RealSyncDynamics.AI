## C-02 — Die erste bezahlte Subscription eines Tenants scheiterte

**Mechanik.** `public.subscriptions` trägt zwei UNIQUE-Constraints: auf
`tenant_id` (`20260811020621`) und auf `stripe_subscription_id`. Der Trigger aus
`20260802000000` legt für jeden neuen Tenant eine Free-Tier-Zeile an, deren
`stripe_subscription_id` **NULL** ist.

`syncSubscription()` im Webhook upsertete mit `onConflict: 'stripe_subscription_id'`.
Postgres behandelt NULLs in Unique-Indizes als verschieden — der Konflikt griff
also nie, der Upsert wurde zum INSERT und verletzte `subscriptions_tenant_id_key`
(23505). Der Handler warf, der Idempotenz-Eintrag wurde zurückgerollt, Stripe
wiederholte, das Ergebnis blieb identisch.

**Warum das jetzt akut war.** Live gemessen am 30.08.: drei von vier Tenants
hielten eine Free-Tier-Zeile mit `stripe_subscription_id = NULL`. Für jeden von
ihnen wäre der nächste Kauf deterministisch in den Fehler gelaufen.

**Dass es ein Fehler und keine Absicht war**, zeigt der zweite Schreibpfad:
`create-trial-subscription` nutzt seit jeher `onConflict: 'tenant_id'`, und die
Reconcile-Migration `20260811020621` nennt genau das als Zweck der Constraint
(„Grundlage für den atomaren UPSERT … (onConflict: 'tenant_id')"). Der Webhook
war der letzte Pfad mit dem falschen Ziel.

**Fix.** `onConflict: 'tenant_id'`. Zusätzlich ein Riegel gegen verspätete
Ereignisse: Stripe garantiert keine Zustellreihenfolge, und ohne Guard könnte ein
spät eintreffendes `customer.subscription.deleted` für ein abgelöstes Abo das
inzwischen aktive überschreiben. Terminale Ereignisse für eine *andere* als die
gespeicherte Subscription werden deshalb ignoriert.

**Keine Migration nötig.** Beide Constraints existieren bereits in Produktion;
der Fix ist reiner Code.

## C-04 — `ai-gateway` war unauthentifiziert erreichbar

**Nachweis** (Produktion, ohne jeden Header — identisch am 09.08. und am 29.08.):

```
POST /functions/v1/ai-gateway   {"op":"health"}     → HTTP 200
  primary : lmstudio.internal … dns error            ← EU-lokaler Pfad unerreichbar
  fallback: anthropic → ok:true                      ← Betreiber-Key, gültig
```

Zum Vergleich liefert `ai-invoke` ohne Header korrekt `401`.

Die Function führt keine eigene Authentifizierung durch. Das Rate-Limit im Code
schützt nicht: `MINUTE_WINDOWS`/`HOUR_WINDOWS` sind Maps im Modul-Scope, leben
pro Isolate, verfallen beim Cold Start und sind per IP-Rotation umgehbar.

Nebenbefund aus derselben Antwort: Der EU-lokale Primärpfad ist per DNS gar nicht
auflösbar. Es ging also **jeder** Gateway-Request in die US-Cloud, unabhängig von
jeder Residenz-Einstellung.

**Fix.** `verify_jwt = true`. Für bestehende Aufrufer folgenlos: alle gehen über
`AiGatewayEdgeClient`, der immer `apikey` + `Authorization: Bearer <key>` setzt —
serverseitig `SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` aus der Edge-Runtime
(`governance-agent`, `classify-document`, `telegram-webhook`, `ai-act-classify`),
im Browser der Anon-Key.

**Erster Schritt, nicht die Lösung.** Der Anon-Key steht per Definition im
Browser-Bundle. Der anonyme Zugriff von außen ist damit zu, der Missbrauch durch
jemanden, der den Key aus dem Bundle liest, nicht. Offen bleiben Tenant-Auflösung,
persistentes Rate-Limit (`_rate_limits` existiert), `ai_tool_runs`-Logging und
Anbindung an `_shared/cost-cap.ts`.

**Wirkt erst nach `supabase functions deploy ai-gateway`.**

## IDOR — `get_compliance_timeline`

SECURITY DEFINER, umgeht damit RLS, nimmt die Mandanten-ID als Aufruferparameter
und prüfte keine Mitgliedschaft:

```sql
WHERE tenant_id = p_tenant_id AND domain = p_domain
```

Der ACL in Produktion war doppelt offen — `=X/postgres` ist der Default-Grant an
PUBLIC, den Postgres beim Anlegen **jeder** Funktion vergibt, dazu ein expliziter
`anon`-Grant:

```
=X/postgres | postgres=X/postgres | anon=X/postgres
| authenticated=X/postgres | service_role=X/postgres
```

**Reproduktion** mit dem öffentlichen Anon-Key und frei gewählter `tenant_id`:
`HTTP 200`. Leer nur, weil `audit_monitor_results` derzeit keine Zeilen hält —
sobald dort Scans liegen, sind Scan-Historie, Risk-Scores und Tracker-Funde
fremder Mandanten abrufbar. Zur Kontrolle: die korrekt geschützte
`onboarding_tenant_policy_packs` antwortet demselben Aufrufer mit `400`.

Die Absicht war bereits eine andere: `20260826000001` führt die Funktion in der
Liste `v_auth` („nur authenticated"), nicht in `v_anon`. Es fehlte das REVOKE des
PUBLIC-Defaults.

**Fix** (`20260901000000`): Mitgliedschaftsprüfung über `is_tenant_member()` in
die WHERE-Klausel, `search_path` gepinnt, `EXECUTE` von PUBLIC und `anon`
entzogen. Nicht-Mitglieder bekommen eine leere Antwort statt eines Fehlers —
dieselbe Linie wie `asset_lifecycle_state` im selben Repo, damit die Funktion
nicht als Existenz-Orakel taugt.

## Offen — bewusst nicht in dieser Arbeit

**Repo ist offener als Produktion.** Gegen ein frisch repliziertes Schema sind
**93** SECURITY-DEFINER-Funktionen für `anon` ausführbar, in Produktion nur **17**.
Die Differenz stammt aus einem Revoke, der laut `20260826000001` „außerhalb des
Repos direkt gegen Prod" angewendet und nie als Migration festgeschrieben wurde.
Ein aus dem Repo neu aufgebautes Environment (`supabase db reset`, Staging, neue
Region) ist damit deutlich offener als die laufende Instanz.

Das hier pauschal zu „reparieren" hieße, denselben breiten Revoke blind zu
wiederholen, der schon einmal Client-Funktionen zerlegt hat — `20260826000001`
existiert genau deshalb. Die Bereinigung gehört entlang der dort bereits
definierten Matrix `v_anon`/`v_auth` hergeleitet und einzeln gegen die Aufrufer
geprüft. Bis dahin hält `security-regressions.db.test.ts` den Stand als sichtbare
Liste fest: Er wächst nicht unbemerkt.

**Aufrufer-Bug in `RiskDashboard.tsx`.** Die Seite übergibt
`(await supabase.auth.getUser()).data.user?.id` als `p_tenant_id` — also die
**User**-ID statt der Tenant-ID. Der Filter `tenant_id = <user_id>` trifft nie,
die Timeline ist immer leer. Vor und nach dem Fix identisch; die Komponente hat
keinen Tenant-Kontext, das Nachziehen wäre eine eigene Änderung an der Seite.

**Altlast-DB-Tests.** Die übrigen Dateien in `test/runtime/db/` sind gegen den
minimalen Harness aus `scripts/test-db/up.sh` geschrieben und scheitern gegen das
voll migrierte Schema an Umgebungsannahmen. Der CI-Schritt läuft deshalb nur
gegen `security-regressions`; die Anpassung ist im Workflow benannt.

und hat eine fest verdrahtete Kette LM Studio → Anthropic → OpenAI. Braucht eine
